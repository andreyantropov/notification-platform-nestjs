# Очередь сообщений (AMQP)

Этот документ описывает топологию очередей, политику доставки сообщений и механизм обработки ошибок в платформе уведомлений.

Взаимодействие между `receive-service` (Producer) и `delivery-service` (Consumer) построено на базе брокера сообщений **AMQP** (RabbitMQ). Архитектура очередей спроектирована максимально просто и надёжно: вся сложная логика повторных попыток вынесена на уровень бизнес-стратегий, а очередь выполняет роль гарантированного транспорта.

---

## 🏗 Топология очередей

Система использует два exchange и две очереди:

| Компонент                         | Тип      | Назначение                                                                                      |
| :-------------------------------- | :------- | :---------------------------------------------------------------------------------------------- |
| `receive.events`                  | Exchange | Direct-exchange для маршрутизации событий от `receive-service`.                                 |
| `delivery.notifications.dlx`      | Exchange | Fanout Dead Letter Exchange. Принимает сообщения, отклонённые воркером, и перенаправляет в DLQ. |
| `delivery.notifications.send`     | Queue    | Основная очередь для всех валидных уведомлений, ожидающих доставки.                             |
| `delivery.notifications.send.dlq` | Queue    | Очередь «мёртвых» писем. Сюда попадают сообщения, которые не удалось обработать.                |

### Схема потока данных

```mermaid
flowchart LR
    RS[receive-service] -- "notification.received" --> EX[receive.events\n(direct)]
    EX --> Q[(delivery.notifications.send)]
    Q -- Consume --> DS[delivery-service]

    DS -- ACK --> Q
    DS -- "NACK (requeue=false)" --> DLX[delivery.notifications.dlx\n(fanout)]
    DLX --> DLQ[(delivery.notifications.send.dlq)]

    DLQ -- Manual Review --> Admin[Administrator]
```

### Bindings

| Source                       | Destination                       | Routing Key             | Описание                                            |
| :--------------------------- | :-------------------------------- | :---------------------- | :-------------------------------------------------- |
| `receive.events`             | `delivery.notifications.send`     | `notification.received` | Маршрутизация новых уведомлений в основную очередь. |
| `delivery.notifications.dlx` | `delivery.notifications.send.dlq` | _(пустой)_              | Перенаправление всех отклонённых сообщений в DLQ.   |

## ⚙️ Принцип работы

### 1. Публикация (Producer)

`receive-service` после успешной валидации запроса публикует сообщение в exchange `receive.events` с routing key `notification.received`.

- **Режим подтверждения:** Сообщения публикуются с флагом `persistent` (доставляются на диск), чтобы пережить перезапуск брокера.
- **Маршрутизация:** Брокер направляет сообщение в очередь `delivery.notifications.send` согласно binding.

### 2. Потребление (Consumer)

`delivery-service` подписывается на очередь `delivery.notifications.send` в режиме **Competing Consumers**.

- Несколько инстансов воркера конкурируют за сообщения. Брокер отправляет каждое сообщение только одному свободному воркеру.
- **Ручное подтверждение (Manual ACK):** Воркер **не** отправляет автоматическое подтверждение (`autoAck: false`). Подтверждение (ACK) отправляется только после того, как стратегия доставки успешно завершит свою работу.

## ❌ Обработка ошибок и Dead Letter Queue (DLQ)

Ключевая особенность архитектуры — **отсутствие автоматических повторных попыток (retry) на уровне брокера**.

### Почему так?

Логика устойчивости к сбоям полностью инкапсулирована внутри **Стратегий доставки** (`delivery-service`).

- Если стратегия видит временную ошибку (например, таймаут SMTP), она сама решает сделать повторную попытку внутри процесса обработки.
- Если стратегия исчерпала лимит попыток или получила критическую ошибку (например, неверный формат контакта), она возвращает результат «Ошибка».

### Механизм попадания в DLQ

Если воркер `delivery-service` завершает обработку сообщения с ошибкой (выбрасывает исключение или явно вызывает `nack`):

1.  Воркер отправляет `NACK` с флагом `requeue: false`.
2.  Сообщение **не возвращается** в основную очередь (чтобы избежать бесконечного цикла ошибок и блокировки очереди).
3.  Благодаря настройке `x-dead-letter-exchange: delivery.notifications.dlx` на основной очереди, брокер автоматически публикует сообщение в DLX.
4.  Fanout-exchange `delivery.notifications.dlx` доставляет сообщение в очередь `delivery.notifications.send.dlq`.

## 🛠 Ручная обработка (Admin Workflow)

Сообщения в очереди `delivery.notifications.send.dlq` требуют ручного вмешательства. Автоматическая доставка из этой очереди не предусмотрена.

**Сценарий работы администратора:**

1.  **Мониторинг:** Администратор отслеживает длину очереди `delivery.notifications.send.dlq` через дашборд RabbitMQ Management или алерты в системе мониторинга.
2.  **Анализ:** Сообщение извлекается из DLQ для анализа причин ошибки (через UI RabbitMQ или специальные скрипты). Частые причины:
    - Недоступность внешнего сервиса в течение долгого времени.
    - Некорректные данные, прошедшие первичную валидацию (edge cases).
    - Баги в коде стратегии.
3.  **Действие:**
    - **Исправить и вернуть:** Если проблема временная или данные можно исправить, сообщение публикуется обратно в exchange `receive.events` с routing key `notification.received` (через UI или скрипт).
    - **Отклонить:** Если сообщение неисправимо (например, удалённый пользователь), оно удаляется из DLQ, клиент уведомляется об этом.
