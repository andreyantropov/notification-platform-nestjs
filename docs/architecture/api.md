# API

Этот документ описывает HTTP API сервиса уведомлений.  
Полная спецификация доступна в интерактивном виде по адресу `/docs/` (Swagger UI).

---

## Аутентификация

Все бизнес-эндпоинты (`/notifications/*`) защищены **JWT-аутентификацией**.  
Клиенты обязаны передавать валидный токен в заголовке:

```http
Authorization: Bearer <JWT>
```

Эндпоинты `/health/*` и `/docs/` — **публичные**, аутентификация не требуется.

---

## Модель доставки: Fire-and-Forget

Платформа работает по асинхронной модели **Fire-and-Forget**:

- HTTP-ответ `202 Accepted` означает **«уведомление принято в очередь»**, а не «уведомление доставлено получателю».
- Фактическая доставка происходит асинхронно через воркеры и может занять от секунд до минут в зависимости от загрузки каналов и внешних провайдеров.

### Как обеспечивается надёжность

Поскольку синхронное подтверждение доставки недоступно, платформа гарантирует надёжность инфраструктурно:

- **Dead Letter Queue (DLQ):** Сообщения, которые не удалось доставить после всех попыток ретраев, сохраняются в DLQ для последующего анализа и ручного/автоматического восстановления.
- **Алертинг:** DevOps-команда получает автоматические оповещения при попадании сообщений в DLQ, превышении порога ошибок канала или деградации производительности очереди.
- **Мониторинг:** Метрики доставки (успехи, сбои, задержки) доступны в observability-стеке для оперативного выявления проблем.

## Версионирование API

Все бизнес-эндпоинты версионируются через **URL-префикс** (`/api/v1/`). Это явный контракт совместимости: клиенты всегда указывают версию, а платформа гарантирует стабильность контракта в рамках мажорной версии.

Версионирование реализовано средствами NestJS (глобальный префикс + `VersioningType.URI`), что обеспечивает единообразие маршрутов и упрощает поддержку нескольких версий при необходимости.

> 💡 Эндпоинты `/health/*` и `/docs/` **не версионируются**, так как являются инфраструктурными и не входят в бизнес-контракт.

---

## Базовый URL

```
{{baseUrl}}/api
```

_(где `{{baseUrl}}` — адрес развёрнутого сервиса)_

## 1. Отправка одиночного уведомления

**Endpoint:** `POST /notifications`

Принимает одно уведомление для доставки одному получателю через один или несколько каналов.

### Структура запроса

```json
{
  "correlationId": "12345",
  "contacts": [
    { "type": "email", "value": "user@company.com" },
    { "type": "bitrix", "value": 12345 }
  ],
  "message": "Приветик через Интернетик!"
}
```

#### Параметры тела запроса

| Поле            | Тип    | Обязательное | Описание                                                                                              |
| :-------------- | :----- | :----------- | :---------------------------------------------------------------------------------------------------- |
| `correlationId` | String | **Да**       | Уникальный идентификатор запроса от клиента (1-128). Используется для сопоставления запроса и ответа. |
| `contacts`      | Array  | **Да**       | Список контактов получателя. Минимум 1, максимум 50. См. формат ниже.                                 |
| `message`       | String | **Да**       | Текст уведомления (1–10 000 символов).                                                                |
| `mode`          | String | Нет          | Стратегия доставки. По умолчанию: `sequence`.                                                         |

#### Формат контакта (`contacts[]`)

Используется дискриминируемый союз (`discriminatedUnion`):

- **Email:** `{ "type": "email", "value": "user@example.com" }`
- **Bitrix24:** `{ "type": "bitrix", "value": 12345 }` (числовой ID пользователя)

#### Стратегии доставки (`mode`)

- `sequence` — отправка прекращается после успеха в первом канале.
- `race` — попытка отправки во все каналы. Успех, если доставлен хотя бы один; ошибка, если все упали.
- `broadcast` — успех, если уведомление доставлено **по всем** доступным каналам; ошибка, если хотя бы по одному каналу отправить уведомление не удалось.

> ⚠️ Поля `id`, `createdAt`, `clientId` генерируются сервером и игнорируются во входных данных.

### Ответы

| Код                         | Описание                                                                            |
| :-------------------------- | :---------------------------------------------------------------------------------- |
| `202 OK`                    | Уведомление успешно принято в обработку. Возвращается полный объект `Notification`. |
| `400 Bad Request`           | Ошибка валидации (пустые контакты, нет сообщения).                                  |
| `401 Unauthorized`          | JWT токен отсутствует или невалиден.                                                |
| `403 Forbidden`             | Пользователь не имеет прав на отправку.                                             |
| `500 Internal Server Error` | Внутренняя ошибка сервиса.                                                          |

#### Пример успешного ответа (`202`)

```json
{
  "id": "a1b2c3d4-e5f6-7890-g1h2-i3j4k5l6m7n8",
  "correlationId": "12345",
  "createdAt": "2026-03-09T10:00:00.000Z",
  "contacts": [{ "type": "email", "value": "user@company.com" }],
  "message": "Ваш заказ №12345 готов к выдаче",
  "mode": "sequence",
  "clientId": "user-123"
}
```

## 2. Пакетная отправка уведомлений

**Endpoint:** `POST /notifications/batch`

Принимает массив уведомлений (от 1 до 50) для массовой рассылки. Валидация выполняется **атомарно**: либо весь пакет принимается, либо весь отклоняется.

### Структура запроса

Тело запроса — объект с полем `items`, содержащим массив уведомлений:

```json
{
  "items": [
    {
      "correlationId": "12345",
      "contacts": [{ "type": "email", "value": "admin@company.com" }],
      "message": "Отчет сформирован",
      "mode": "broadcast"
    },
    {
      "correlationId": "54321",
      "contacts": [{ "type": "bitrix", "value": 999 }],
      "message": "Требуется согласование"
    }
  ]
}
```

### Принцип атомарной валидации

Сервис валидирует **весь массив целиком** перед постановкой в очередь:

- ✅ **Все элементы валидны** → пакет принимается, возвращается `202 Accepted` с массивом результатов.
- ❌ **Хотя бы один элемент невалиден** → весь пакет отклоняется с `400 Bad Request` и описанием ошибок.

> 💡 Такой подход устраняет необходимость частичной обработки и сопоставления результатов. Клиент получает гарантию: если запрос принят, то **все** уведомления из пакета будут доставлены.

### Структура ответа

#### Успех (`202 Accepted`)

```json
{
  "items": [
    {
      "id": "a1b2c3d4-e5f6-7890-g1h2-i3j4k5l6m7n8",
      "correlationId": "12345",
      "createdAt": "2026-03-09T10:00:00.000Z",
      "contacts": [{ "type": "email", "value": "admin@company.com" }],
      "message": "Отчет сформирован",
      "mode": "broadcast",
      "clientId": "user-123"
    },
    {
      "id": "a1b2c3d4-e5f6-7890-g1h2-i3j4k5l6m7n8",
      "correlationId": "54321",
      "createdAt": "2026-03-09T10:00:00.000Z",
      "contacts": [{ "type": "bitrix", "value": 999 }],
      "message": "Требуется согласование",
      "mode": "sequence",
      "clientId": "user-123"
    }
  ]
}
```

Массив `items` в ответе строго соответствует порядку элементов в запросе.

#### Ошибка валидации (`400 Bad Request`)

```json
{
  "message": "Валидация пакета не пройдена",
  "errors": [
    {
      "index": 1,
      "field": "contacts",
      "message": "Список контактов не должен быть пустым",
      "code": "too_small"
    }
  ]
}
```

Поле `index` указывает позицию невалидного элемента в исходном массиве, что позволяет точно локализовать проблему.

### Коды ответов

| Код                | Описание                                                                              |
| :----------------- | :------------------------------------------------------------------------------------ |
| `202 Accepted`     | Весь пакет валиден и принят в обработку. Возвращается массив объектов `Notification`. |
| `400 Bad Request`  | Нарушена структура пакета или валидация одного/нескольких элементов не пройдена.      |
| `401 Unauthorized` | JWT токен отсутствует или невалиден.                                                  |
| `403 Forbidden`    | Пользователь не имеет прав на отправку.                                               |
| `500`              | Внутренняя ошибка сервиса.                                                            |

## Healthcheck Эндпоинты

Используются оркестраторами (Kubernetes) для контроля состояния сервиса.

| Endpoint            | Тип       | Описание                                                             |
| :------------------ | :-------- | :------------------------------------------------------------------- |
| `GET /health/live`  | Liveness  | Процесс запущен и отвечает. Если падает — контейнер перезапускается. |
| `GET /health/ready` | Readiness | Сервис готов принимать трафик (брокер и зависимости доступны).       |

---

## Рекомендации для интеграторов

1.  **Используйте пакетную отправку** для массовых рассылок (до 50 шт.) — это снижает нагрузку на сеть и сервис.
2.  **При `400` анализируйте поле `errors[].index`** для точечного исправления невалидных элементов перед повторной отправкой **всего пакета**.
3.  **Повторяйте запрос при `5xx`** с экспоненциальной задержкой.
4.  **Сохраняйте `id` уведомлений** из ответа для корреляции с логами и трейсами.
5.  Если уведомление критично и требует подтверждения доставки конечному пользователю, реализуйте **бизнес-уровневое подтверждение** на стороне получателя (например, ссылка-подтверждение в письме, callback от пользователя в Bitrix24). Платформа не предоставляет API для опроса статуса доставки.
